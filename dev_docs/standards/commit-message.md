# 提交信息规范

提交信息使用下面的结构：

```text
<TYPE>: <一句话说明>

WHY:
<为什么需要这次改动，说明问题、背景或目标>

WHAT:
<具体改了什么，列出主要文件、模块或行为变化>

TEST:
<执行过的验证命令和结果；如果没有测试，写明原因>
```

## TYPE 类型

- `FIX`：修复错误、缺陷或回归问题。
- `NEW`：新增一个完整的功能、模块或独立能力。
- `ADD`：补充已有功能的支持内容，例如脚本、配置、接口或资源。
- `CHANGE`：修改已有功能或用户可见行为，但不属于缺陷修复。
- `REFACTOR`：重构代码结构，不改变预期功能。
- `BUILD`：构建系统、工具链、编译选项或打包流程调整。
- `DOCS`：文档、注释或开发流程说明调整。
- `TEST`：新增、修改或整理测试和验证工具。
- `CHORE`：不影响功能的维护性工作，例如依赖、格式或仓库整理。

每次提交只选择一个最主要的类型。`NEW` 通常用于新增完整能力，`ADD` 用于
向已有能力补充组成部分；如果改动同时涉及多个方面，按主要目的选择类型，
并在 `WHAT` 中说明其他影响。

## 编写要求

1. 标题使用动词开头，简短说明结果，不在标题中堆叠文件名。
2. `WHY` 说明动机，不要只重复标题。
3. `WHAT` 说明实现范围和重要行为变化。
4. `TEST` 写出实际执行的命令和结果；硬件尚未验证时明确写出。
5. 一个提交尽量只包含一个可独立回滚的逻辑变化。

## 示例

```text
BUILD: add incremental firmware build wrapper

WHY:
减少日常编译时重复输入 CMake 和 Ninja 命令的工作量。

WHAT:
新增 scripts/build.sh，支持 RS485/CAN、Debug/Release、增量和全量编译。

TEST:
scripts/build.sh --backend RS485 --full --jobs 2
scripts/build.sh --backend CAN --jobs 2
结果：两个后端均成功生成 ELF、HEX、BIN 和 MAP 文件。
```
